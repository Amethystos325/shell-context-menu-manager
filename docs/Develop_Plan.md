# Shell UI 管理器（Electron）MVP 开发计划

## 1. 目标

基于 Electron（JS/TS 技术栈）开发一款桌面应用，通过 UI 可视化管理 Nilesoft Shell 右键菜单配置，替代手工编辑 `shell.nss` 的高门槛流程，并保证配置变更安全可回滚。

开发环境基线：统一使用 `Node.js v22`（建议锁定到团队一致的小版本）。

## 2. MVP 功能清单

1. 配置文件路径设置、读取、保存。
2. 菜单树可视化编辑：`menu / item / separator` 增删改排。
3. 系统菜单规则编辑：`modify / remove`（至少支持 `find`、可见性、位置、菜单归类等基础字段）。
4. 常用属性编辑：`title`、`cmd`、`args`、`type`、`mode`、`image`、`tip`。
5. 变量辅助输入：`@sel.path`、`@sel.dir`、`@sel.file.name` 等。
6. 语法校验与错误提示（保存前阻断）。
7. 保存前 Diff 预览。
8. 自动备份与一键回滚。
9. 应用配置动作（触发刷新流程或给出明确操作指引）。
10. 日志面板（记录读取、校验、保存、回滚、应用结果）。

## 3. 开发进度跟踪方式

进度文件位置：`docs/Develop_Progress.md`

使用方法：
1. 开始某一阶段时，将该阶段状态更新为 `In Progress`，并记录开始日期。
2. 完成某一阶段时，将状态更新为 `Done`，记录完成日期，并补充“已完成工作”。
3. 每完成一个阶段，都要同步填写“下一阶段应完成工作”，作为后续执行清单。
4. 如发生阻塞，状态更新为 `Blocked` 并在该阶段记录阻塞原因与解除条件。

## 4. 分阶段开发计划

总建议周期：4 周（单人前端主导）。

## 阶段 0：需求冻结与交互定稿（0.5-1 天）

目标：明确 MVP 边界，避免开发中途频繁改需求。

要做什么：
1. 定义 MVP 字段范围（哪些属性可编辑，哪些先不支持）。
2. 输出页面草图：配置页、编辑页、发布页、日志页。
3. 定义关键用户流程：打开配置 -> 编辑 -> 校验 -> Diff -> 保存 -> 应用 -> 回滚。
4. 定义错误场景：语法错误、路径无权限、写入失败、回滚失败。

阶段产出：
1. 一份功能冻结清单。
2. 一份页面流程图（低保真即可）。

验收标准：
1. 每个功能都能映射到具体页面与按钮。
2. 开发过程中不再新增非必要字段。

## 阶段 1：工程底座与安全通道（2-3 天）

目标：搭建可持续开发的 Electron 基础工程。

要做什么：
1. 在 `Node.js v22` 环境下初始化 `Electron + TypeScript + Vite + React/Vue` 工程。
2. 拆分进程职责：`main`（文件/命令）、`preload`（白名单 API）、`renderer`（UI）。
3. 配置安全基线：
   1. `contextIsolation: true`
   2. `nodeIntegration: false`
   3. IPC 通道白名单 + 参数校验
4. 建立统一日志模块（按级别输出到文件与 UI）。
5. 建立错误码规范（如 `E_PARSE`、`E_PERMISSION`、`E_WRITE_FAIL`）。

阶段产出：
1. 可启动桌面壳。
2. 可调用 IPC 读写本地测试文件。
3. 基础日志可见。

验收标准：
1. 渲染层不能直接访问 Node 文件 API。
2. IPC 接口可追踪、可审计。

## 阶段 2：配置内核（解析、模型、序列化、校验）（4-5 天）

目标：先打通“正确读写配置”的核心链路。

要做什么：
1. 设计统一领域模型（菜单节点、规则节点、全局设置）。
2. 实现最小语法子集解析：
   1. `menu/item/separator`
   2. `modify/remove`
   3. `import`（至少识别并保留）
3. 实现模型到文本的序列化器。
4. 实现校验器：
   1. 必填校验（如 `item.title/cmd`）
   2. 基本语法校验（括号/引号）
   3. 字段合法性校验（`type`、`mode` 值）
5. 实现 Diff 数据结构（旧文本 vs 新文本）。

阶段产出：
1. CLI 或内部测试入口可完成“读 -> 改 -> 写 -> 再读一致”。
2. 校验结果可返回定位信息（行或节点）。

验收标准：
1. 10+ 份示例配置 round-trip 后结构不崩。
2. 语法错误可稳定拦截，不允许直接覆盖写入。

## 阶段 3：可视化编辑器（5-6 天）

目标：完成用户可用的主编辑界面。

要做什么：
1. 实现左侧菜单树（拖拽排序、增删节点、复制节点）。
2. 实现中间属性面板（按节点类型动态表单）。
3. 实现右侧源码视图（至少支持查看与刷新；编辑能力可先受限）。
4. 实现变量快捷插入（`@sel.path` 等）。
5. 增加“脏状态”提示和离开确认。

阶段产出：
1. 用户可在 UI 完整创建一个可执行菜单组。
2. 修改任意字段后可实时反映到预览文本。

验收标准：
1. 连续编辑 30 分钟不出现状态错乱。
2. 保存后的配置被 Shell 正常加载。

## 阶段 4：发布闭环（规则、Diff、备份、回滚、应用）（4-5 天）

目标：把“能编辑”升级为“可安全发布”。

要做什么：
1. 完成 `modify/remove` 专用编辑器（列表化）。
2. 保存前弹出 Diff 预览，支持确认/取消。
3. 实现自动备份策略（按时间戳，保留最近 N 份）。
4. 实现回滚中心（备份列表 + 预览 + 恢复）。
5. 实现应用配置动作：
   1. 自动执行刷新命令（有权限时）
   2. 自动失败时给出手动步骤
6. 日志页展示每次发布流水。

阶段产出：
1. 完整发布链路：校验 -> Diff -> 备份 -> 写入 -> 应用 -> 记录。
2. 一键回滚可恢复到指定历史版本。

验收标准：
1. 任意失败场景都不会丢配置。
2. 回滚成功率达到 100%（在可读备份前提下）。

## 阶段 5：稳定性测试与交付（3-4 天）

目标：确保 MVP 可安装、可试用、可排错。

要做什么：
1. 回归测试核心流程：
   1. 新建菜单
   2. 修改规则
   3. 保存应用
   4. 回滚恢复
2. 异常测试：
   1. 无权限目录写入
   2. 非法语法输入
   3. 目标文件被占用
3. 打包安装器（Windows）。
4. 输出使用手册（首次配置、回滚、排错）。
5. 输出已知问题列表。

阶段产出：
1. 可安装版本（内测包）。
2. 最小测试报告和问题清单。

验收标准：
1. 核心 20+ 用例通过。
2. 连续保存与回滚压力测试稳定。

## 5. 开发注意要点

1. 先保证正确性，再做高级体验。
2. 保存前必须校验，写入前必须备份。
3. 任何失败都要有“可理解报错 + 可执行下一步”。
4. IPC 不暴露泛化命令执行能力，只暴露固定用途接口。
5. 路径与命令参数必须做转义与白名单限制。
6. 编辑器状态必须可恢复（防止误关闭丢失）。
7. 不强行“格式化重写”全部配置，尽量减少无关变更。

## 6. 阶段完成定义（DoD）

每个阶段完成需同时满足：
1. 功能验收通过（按本阶段验收标准）。
2. 关键错误路径已人工验证。
3. 有可运行构建产物。
4. 有阶段变更记录（做了什么、已知问题、下一阶段风险）。
